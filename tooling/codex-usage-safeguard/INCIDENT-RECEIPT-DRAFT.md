# Incident receipt: offline design candidate

The safeguard retains the originating transport incident and each send attempt. Concierge records its receipt separately, keyed by the existing incident UUID. Recovery of a transport route does not itself establish receipt, owner acceptance, or completed repair. A successful send is only submission; an uncertain outcome is never automatically retried.

## Candidate storage

Use a private, restart-persistent receipt journal outside the release tree, scoped to the existing safeguard state directory. Do not reuse or replace the transport health file: it is reconstructible and clears the active incident on recovery. The candidate has one writer, Concierge, and a read-only safeguard consumer; the safeguard continues to own its existing incident ledger. Files and their parent directories must be owner-only and reject symlinks. Store location, cross-chat file access, permissions, writer serialization, backup, and recovery ownership require actual qualification before adoption. If an existing qualified store meets the contract, select it instead; neither a production store nor a new service is created by this design.

The inspected existing installation uses `transport/health.json` beneath its runtime state directory; metadata readback showed both directories owned by the operating user with mode 0700 and the health file mode 0600. This does not establish another chat's sandbox access, independent custody, or recoverability. Its observer writes the file; route recovery removes the active incident, so it is unsuitable as the receipt journal. The installed Rolecasting mailbox helper uses SQLite transactions and `synchronous=FULL`, but its documented acceptance is offline, it has no bound Concierge store or authenticated native evidence, and it does not itself record the named owner's acceptance and continuation as this contract requires. No existing qualified store was found in these bounded sources.

For a single Concierge writer, a separate `runtime/incident-receipts.json` can reuse the safeguard's existing `storage.py` private reader and fsync/atomic-replace writer; a lock serializes overlapping writer invocations. This avoids a database dependency while preserving a separate receipt history. It is an offline candidate path only, not an existing file or selected production binding. Concierge would be the writer and recovery owner, and the safeguard would read only; actual sandbox access, lock security, corruption and interrupted-write behavior must be demonstrated before selection. SQLite's transaction model may become necessary if those constraints do not hold, but its prototype is not a dependency.

## Record contract

One immutable incident identity includes the originating incident UUID and the sender and recipient native host/thread identities. Each immutable attempt identity records the actual submitting caller, target, payload correlation and creation time. Append observations rather than overwriting them:

- submission outcome, including unknown or refused;
- receiver/attempt-correlated native evidence of receipt;
- actual named repair-owner acceptance with evidence;
- owned continuation and its trigger;
- completion and its evidence.

Conflicting observations remain visible. A record's assertion is not authentication of native evidence. Receipt is not owner acceptance, and owner acceptance is not completion. A later attempt requires conclusive nondelivery, a recorded owner decision and still-valid authority. Missing readback, empty history or process restart does not establish nondelivery.

Readback must return the immutable incident, all attempts and observations, and unresolved uncertainty without mutating the record. A replacement consumer must reopen the same store and recover pending obligations. Schema/version validation must fail closed without deleting or reconstructing evidence.

An attempt carries its incident UUID, caller host/thread, target host/thread, and a unique attempt ID embedded in the exact submitted payload. A receipt observation records the receiver's native thread, turn and message identifiers plus the correlated attempt and a durable evidence reference. The consumer verifies those identifiers against an actual native read; a journal entry alone is an untrusted assertion. An owner-acceptance observation records the accepting chat identity, native message reference, and the specific incident. The continuation records its accountable owner, next action or trigger, and evidence of that owner's acceptance. Until both owner acceptance and a recoverable continuation are evidenced, the incident remains pending even after receipt.

The offline acknowledgment candidate is an exact assistant message consisting of `QUOTA-ACK/1 ` and compact ASCII JSON with sorted keys `attempt`, `incident`, and `kind`. Kinds are `receipt`, `owner_accepted`, and `continuation`; continuation also has a nonempty `next_action` key. Concierge's receipt must come from the bound Concierge chat; owner acceptance and continuation must come from the separately bound repair-owner chat. Readback binds host, thread, turn and message IDs, requires one exact assistant message, and does not accept user text or a quoted line as an acknowledgment. A bounded read that misses a message remains pending and is not evidence of nondelivery. This is an offline grammar, not proof that the genuine caller can retrieve these messages or that evidence is authenticated in production.

The candidate journal must commit each immutable observation atomically before reporting success. An interrupted write must leave the last committed history readable or return an explicit integrity failure; it must not infer that the attempted action did or did not occur. A duplicate exact observation is idempotent; changed data under the same immutable identifier is rejected. Simultaneous writes serialize and retain both valid observations. Restart opens the existing journal without silently creating a replacement. These are requirements for the implementation and its crash/partial-write tests, not claims about a deployed store.

## Verification before adoption

Isolated tests use temporary private storage and fixture recipients to cover duplicate identity, changed-content conflicts, separate states, restart, concurrent writers, unknown and contradictory observations, and refusal to retry uncertain attempts. Native qualification separately establishes the genuine safeguard caller's permission, actual correlated delivery and acknowledgment, and recovery by the designated owner. A passing offline test does not establish those facts. The existing service, episode, caller, delivery and lock state remain unchanged until the concrete reviewed adoption decision.

The operator selected 95% used as the desktop-alert threshold for failed agent intake, with unknown activity or quota treated conservatively; this is not the protective-pause threshold. A supported, fresh activity/quota observation and intake-failure determination still have to be connected before this can be applied by the observer. Unknown submission is not proven nondelivery. Preserve and reconcile it rather than retrying it or treating a bounded empty native read as a negative receipt.

The emergency alert records its attempt before notification when its private notice record is available. If that record cannot be read or written, the observer still attempts the alert and throttles further attempts within the running process. A restart can cause another attempt within an hour, including after a failed or uncertain notification. Preserve unreadable state; do not replace it to manufacture a throttle record.

## Consumer invocation and recovery

After the separate handover has bound the store, caller, recipients and permissions, Concierge reads the originating private outbox and records an incident with `incident_receipts.py --store <store> incident --input <private-json>`, then records its attempt with `attempt --incident <incident-id> --input <private-json>`. The incident input contains `incident_id`, `sender`, `sender_host`, `recipient`, and `recipient_host`. The attempt input contains `id`, `caller`, `caller_host`, `target`, `target_host`, and the exact `payload`. The input files must be owned, private regular files. `init` is a one-time authorized setup action; never use it to replace a missing or unreadable recovery store.

Append each observation with `observation --incident <incident-id> --input <private-json>`. Every observation contains `id`, `kind`, `attempt_id`, `evidence`, `actor`, `host`, `turn`, and `message`. A `received` observation also names `submission_turn` and `submission_message`. A `continuation` also names `next_action`. These records are assertions until the configured genuine caller independently matches the native message and acknowledgment. `show --incident <incident-id>` reads the retained record without changing it. A missing, malformed, inaccessible, or contradictory record remains pending.

`reconcile_incident.py --config <private-config> --state-dir <state-dir> --incident <incident-id>` reads the existing outbox and receipt store and uses the inherited native route. It never sends, retries, resets, changes accounts, or releases work. Its output describes exact matches; it is not proof that the native caller or channel has been qualified. On an uncertain attempt, preserve it and investigate the correlated native evidence. Absence from a bounded read is not nondelivery. A later attempt requires conclusive nondelivery and an explicit owning-task decision; this candidate does not automate that retry.

The observer's draft new-routing mode is activation-blocked until the reviewed candidate and concrete adoption steps are ready. The existing installed service, old receipts, caller and episode history remain the recovery baseline. Real caller-to-recipient delivery, acknowledgment, current roles, store access and operator-approved installation remain separate gates.
