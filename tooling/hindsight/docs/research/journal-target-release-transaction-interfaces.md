# Target-release journal transaction-interface verification

**Disposition: no; the bounded source packet is sufficient for that conclusion.** Hindsight 0.8.4 exposes pooled connection acquisition, generic SQL methods, wrapper-level transaction contexts, transaction-local retain helpers, and transactional worker claims. The inspected release does not expose or route the complete accepted trusted-adapter contract: stage-specific transaction controls, immediate durability verification, acknowledged-versus-ambiguous commit outcomes, exact stage-resolution methods, activation-bound session continuity with a nonpersistent witness, or monotonic fencing across every writer path. Those capabilities remain successor additions or integration work. This report establishes source shape, not runtime behavior.

## Accepted boundary used for comparison

The accepted design keeps `J`, `P`, `R`, `M`, and `V` in the target PostgreSQL database. A trusted adapter owns each stage from connection acquisition and `BEGIN` through the single protected call, an immediate effective `synchronous_commit=on` check, and the driver COMMIT return; callers receive neither the connection nor an opportunity to insert SQL. Caller acknowledgement then requires a separate authoritative protected read of the exact durable receipt or committed-result mapping; neither the protected return nor driver COMMIT return alone is acknowledgement ([transaction boundary](https://github.com/nisavid/agents/blob/90108b516f5a1c460980a93670348f6e228124f2/tooling/hindsight/docs/journal-publication-design.md#L20-L43)). `M` must run at serializable isolation and atomically combine the target compare-and-swap, receipt, target generation, and lineage advance. Lost acknowledgement is resolved from the exact receipt, generation, and postimage without remutation ([mutation contract](https://github.com/nisavid/agents/blob/90108b516f5a1c460980a93670348f6e228124f2/tooling/hindsight/docs/journal-publication-design.md#L819-L903)).

Recovery distinguishes committed, conclusively aborted, and still ambiguous attempts; a bounded unresolved `M` returns `STAGE_AMBIGUOUS(M)` and never retries or verifies ([ambiguity contract](https://github.com/nisavid/agents/blob/90108b516f5a1c460980a93670348f6e228124f2/tooling/hindsight/docs/journal-restart-design.md#L655-L707)). Activation and every `M` share one dedicated backend session and session-local capability witness. Connection replacement, adapter or server restart, or continuity uncertainty fences the old epoch ([continuity contract](https://github.com/nisavid/agents/blob/90108b516f5a1c460980a93670348f6e228124f2/tooling/hindsight/docs/journal-restart-design.md#L709-L764)). At accepted revision `90108b516f5a1c460980a93670348f6e228124f2`, the public FW03 source interface has an incarnation-proof parameter. That accepted-source roster does not contain the IA11/admission members added by issue 107.

The issue-107 proposal overlay is separately identified by the immutable proposal-artifact SHA-256 in the PostgreSQL schema record. It derives the authenticated caller, immutable identity kind and stage, invocation/recovery mode, recovery-request presence, derived work class, and protected continuity-session result before request, refusal, reservation, accounting, or start mutation. C16 admits J/P/R, C17 admits only M on the activation-bound session, C18 admits only V, and C19 admits only transaction resolution, ambiguity query, and reconciliation. The runner enters FW02/FW03 first. For C17/M, that function acquires applicable ranks 1/2 and calls the O16-owned IA11 projection; IA11 accepts no caller/session override, locks the current active-epoch and activation/continuity chain at rank 3, returns typed AW04 admission with only the opaque RX03 M-admission ID and authenticated RX05 adapter-incarnation ID, and retains those locks through the outer commit or rollback. FW02/FW03 then acquire rank 5. FW02 owns atomic RW01 insertion or replay equality. The proposal-only `FW03(reservation)` accepts no incarnation proof, owns fresh-to-RW01 equality after rank 5, and only then persists RW04/RW05/RS14 and returns START. For M/AW04 only, it copies the IA11-derived `adapter_incarnation_id` into both the transaction identity and start; every J/P/R/V/RECONCILIATION identity and start omits that field. These members remain proposal-only until they have an accepted source identity; this report does not assign one.

## Downstream planning implications

The fixed [journal transaction and recovery interface](journal-transaction-recovery-interfaces.md) specifies one adapter-owned protected-transaction runner, protected-entrypoint-first call placement, the per-entrypoint lock order, exact acknowledgement/RW01 readback behavior, and one dedicated continuity-session lifecycle. An implementation may evaluate the typed wrapper scope, generic SQL passthrough, and a separately pinned raw-driver interface only as candidate extraction seams; none is assumed to satisfy the contract. Commit uncertainty begins when a commit request may have reached PostgreSQL, and both the protected return and driver COMMIT return remain provisional until a separate authoritative protected read matches the durable receipt or committed-result mapping. Session loss fences the old epoch without erasing the historical admission carrier. Under the issue-107 proposal, PostgreSQL would derive the M/AW04 `FW03` transaction identity and start with their IA11-derived `adapter_incarnation_id`; J/P/R/V/RECONCILIATION identities and starts omit the field. The no-client-proof form remains proposal-only. Accepted revision 90108 retains its FW03 incarnation-proof operand.

[Define journal mutation and compatibility integration](https://github.com/nisavid/agents/issues/108) cannot treat the current retain orchestrator as the atomic mutation merely because its mini-batches use transactions or because one conditional callback shares a connection. The plan must identify the exact target rows and every writer, route the selected compare-and-swap through the activation-bound connection, and commit the target change with the protected `M` receipt, generation, and lineage. It must also place outbox, ANN, metadata, hooks, cache work, and maintenance on explicit sides of that boundary. The current low-level connection parameters are possible extraction seams, not evidence that this integration already exists. Historical-reader results remain `authority=NONE` and cannot enter `J/P/R/M/V` ([accepted reader boundary](https://github.com/nisavid/agents/blob/90108b516f5a1c460980a93670348f6e228124f2/tooling/hindsight/docs/journal-compatibility-design.md#L573-L612)).

[Set journal implementation sequencing and evidence gates](https://github.com/nisavid/agents/issues/109) may treat the accepted-source definitions and the separately digest-bound issue-107 proposal as planning inputs, not implemented seams. It should still order evidence by dependency: implement typed adapter outcomes and protected calls, including proposal IA11; qualify protected-entrypoint-first placement, the O10-only nested ACL, exact two-site/branch cardinality, typed two-ID result, RX03/RX05 origin, atomic RW01 insertion, rank-3-before-rank-5 locks, retention through outer commit/rollback, proposal FW03 equality after rank 5 before persistence, M/AW04-only incarnation copying, non-M field absence, and pre-rank-3 replacement versus post-rank-3 waiting; inject failures before commit, after server commit, and before the separate authoritative acknowledgement read; prove exact replay/readback after session loss, deterministic denial/refusal/conflict outcomes, and no duplicate `M`; then qualify session replacement, adapter/server restart, pool behavior, physical durability, and the exact release artifact. Issue 109 remains open, and source availability alone is not a runtime result.

## Proposal-only successor FW02/FW03 admission seam

This seam is the issue-107 proposal inventory, keyed by the immutable proposal
artifact digest. It is not in accepted revision 90108. A future target
integration would have to preserve this exact protected-function projection if
the proposal receives an accepted source identity:

| Caller | Admitted immutable work | Invocation and session predicate |
| --- | --- | --- |
| `C16` | J/P/R stage identity | `FORWARD/NONE/NONE` or `RECOVERY/ADVANCE_STAGE/non-NONE` on C16's qualified transaction connection |
| `C17` | M stage identity only | the same forward/recovery stage modes, only on the active epoch's exact bound backend/session witness and adapter incarnation |
| `C18` | verification identity, derived V | `FORWARD/NONE/NONE` or `RECOVERY/VERIFY_STAGE/non-NONE` on C18's evidence-only connection |
| `C19` | transaction-resolution, ambiguity-query, or reconciliation identity only | its matching `RECOVERY` mode and non-`NONE` request on C19's qualified current connection; any subject-stage field grants no stage callable |

The protected function derives `work_class` after admission. Every complement
tuple fails before any request/refusal record, observation, reservation,
accounting, or start effect. The inspected 0.8.4 wrapper exposes no such
role-to-identity admission seam; generic SQL and transaction contexts are not
evidence that it exists.

For C17/M, the proposed successor seam is specifically the O16-owned IA11
projection called only by O10 at one guarded site inside each of FW02/FW03.
The runner enters the protected function first. FW02/FW03 acquire every
applicable rank-1 dependency and then every applicable rank-2 dependency;
neither rank may be skipped. IA11 then derives the current
active epoch, activation binding, backend session, witness, continuity-session
identity, completed fence binding, capability, and adapter incarnation without
caller overrides; locks that projection at rank 3 before rank 5; returns only
`{row_id=AW04,work_class=M,m_work_admission_identity={m_work_admission_id,adapter_incarnation_id}}`;
or denial. It retains its locks through the outer commit or rollback. A
replacement attempted after those rank-3 locks are held waits until that outer
boundary; it cannot race through to admission denial before rank 5. A
replacement that wins before rank 3 may determine the subsequently locked
binding or deny admission. FX01/RX03 owns the
opaque unique admission ID, and RX05 owns the authenticated live-session
incarnation ID. FW02 obtains one fresh IA11 result for every candidate-AW04
initial reservation, new refusal, exact reservation replay, exact refusal
replay, or repeated unresolved request and stores it atomically with RW01.
The proposal-only `FW03(reservation)` accepts no incarnation proof; accepted
revision 90108 instead retains its proof parameter. Proposed FW03 obtains one fresh IA11
result for every first start, acknowledgement-uncertain repeat, or
already-started repeat. FW02 owns fresh-to-RW01 equality on replay after rank
5. FW03 owns fresh-to-RW01 equality after rank 5, copies the incarnation into
the M transaction identity and start, and only then persists RW04/RW05/RS14
and returns START. All ranked locks end only at the transaction's
commit or rollback. The two M/AW04 positive expansions require the field in
both complete bodies; the other eleven positive J/P/R/V/RECONCILIATION
expansions omit it from both bodies. Non-AW04 branches, FW01/FW08, and adapters
call IA11 zero times. After the driver returns from COMMIT, acknowledgement
requires a separate authoritative protected read. FW01/FW08 exact readback
returns the historical carrier after session loss and never reauthorizes M.
Qualification must cover the positive forward/recovery rows, the full ACL

The inspected release exposes neither IA11 nor an equivalent protected owner
